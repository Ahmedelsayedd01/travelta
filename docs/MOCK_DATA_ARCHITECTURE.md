# Mock Data Architecture: `@travelta/mock-server`

## 0. As built (Milestone 3)
- **Operation catalogue:** `@travelta/schemas/operations` declares each operation's input and output Zod schemas, its future REST route (`http.method` + `path`), `auth`, and `demoOnly`. The client is typed from it, and the mock server validates against it (outputs too, in dev builds).
- **Composition:** apps call `createMockApi({ persistence })` from `@travelta/api-client/mock`. Apps never import `@travelta/mock-server`, and a lint rule enforces that.
- **Server pipeline:** latency and failure simulation (business operations only), then a serial queue, input validation, the handler inside an undo-log transaction, output validation, debounced persistence and events.
- **Persistence:** web uses IndexedDB through `idb-keyval` (`apps/web/src/lib/persistence/indexeddb.ts`), with cross-tab sync via `BroadcastChannel` + `reload()`. Mobile uses chunked AsyncStorage through `createKeyValuePersistence` (logic and tests in `@travelta/api-client`). Both flush on page hide or app background.
- **Seed anchoring:** seeds are built from the **start of the current UTC day**, so every reset on the same day gives a byte-identical dataset (same fingerprint), while history stays relative to today.
- **Demo tools:** web has a floating panel (`NEXT_PUBLIC_DEMO_TOOLS=false` hides it). Mobile has a `/demo` screen. Both offer status/fingerprint, clock moves, latency and failure rate, reset, export (download or share sheet) and import (file input or document picker, Zod-validated, confirmed before replacing).
- **Native runtime:** `structuredClone` is provided on Hermes by Expo's runtime polyfill (`expo/src/winter`).

## 1. Shape


## 2. Call path
`api-client` → `MockTransport.call('bookings.cancel', input)` → `server.handle(op, input, token)`:
1. Simulated latency (default 150–600 ms, jitter; 0 in tests).
2. Build `RequestContext` from the token (401 if invalid).
3. Validate the input with the Zod schema (422).
4. Service → permission check → domain rules → repositories inside `runInTransaction`.
5. Map to the audience DTO, validate the output in dev, and `structuredClone` it so the UI never holds live references.
6. Emit events, persist (debounced 300 ms; flushed on `visibilitychange`/`beforeunload`).

When the HTTP backend is ready, `HttpTransport` replaces step 1 onward with `fetch`. Nothing in the apps changes.

## 3. Persistence
| Platform | Adapter | Notes |
|---|---|---|
| Web | IndexedDB via `idb-keyval`, key `travelta:db:v{schemaVersion}` | Stores the whole snapshot (well under quota). One snapshot write per transaction batch. |
| Mobile | AsyncStorage, same key | Large-value limit on Android (~6 MB default per key in some setups) → the snapshot is **chunked by collection**. |
| Tests | In-memory (no-op) | Deterministic |

**Export / import:** the Demo panel exports the whole snapshot as versioned JSON (`travelta-demo-<date>.json`) and imports one (schema-version check, Zod validation, confirm before replacing). This works on web (download/upload) and mobile (share sheet / document picker). It is the only way to move data between devices. **There is no automatic sync between web and mobile.**

**Reset:** the Demo panel ("Reset demo data") or `api.demo.reset()` clears storage and rebuilds the deterministic seed. A seeded PRNG plus a fixed seed clock mean every reset gives an identical dataset.

**Multi-tab (web):** a `BroadcastChannel('travelta-db')` tells other tabs to reload the snapshot after a commit. Last writer wins; this is a prototype limitation and is documented.

## 5. Supplier simulation
- **Adapter contract** (same as future real adapters): `search(params) → Offer[]`, `recheck(offerRef) → Offer | PriceChanged | Unavailable`, `book(offerRef, travellers, idempotencyKey) → { status: confirmed|pending|rejected, supplierRef? }`, `cancel(supplierRef) → { fee, status }`.
- **Deterministic behaviour** from `hash(offerRef)`:
  - ~85% confirm, 8% pending → confirm after N seconds, 4% reject, 3% price changed on recheck
  - search latency 300–1200 ms
  - timeout scenario available.
- **Override**: the Demo panel can force the next response (`confirm | reject | price_changed | timeout | sold_out`).
- Each call writes a `SupplierRequestLog` (shown on booking detail for admins).
- Manual and network suppliers: `book()` returns `pending (awaiting_supplier)`. Confirmation happens in the supplier portal or the agency ops board.

Vodafone Cash, InstaPay and bank transfer collections are recorded instantly in the back office. No external calls of any kind.

## 7. Notifications
The event bus turns events into `Notification` records (in-app) and **previews** of email/WhatsApp messages, rendered from templates per locale and viewable in an admin "Outbox" 🔶. Nothing is sent.
